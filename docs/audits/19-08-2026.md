# Auditoría miyi-app

**Fecha** 2026-08-19
**Rama** `feat/new-balance-kpi` @ `7253139`
**Alcance** `app/` · `routes/` · `database/` · `config/`
**Base** 115 archivos PHP, ~11.100 líneas

**66 findings**: 8 P0 · 22 P1 · 25 P2 · 11 P3 · + 6 a verificar

Auditoría de solo lectura: no se modificó código, no se crearon commits, no se corrieron
migraciones ni scripts que muten datos, no se cambió configuración. La verificación fue lectura
de archivos y `grep`. No se corrieron tests porque no existe suite (removida a propósito según
`AGENTS.md`; confirmado: no hay `tests/`, `phpunit.xml` ni `require-dev`).

---

## Executive summary

1. **La autorización es decorativa fuera de dos módulos.** Solo `deliveries` y `account-entries`
   aplican policies. En todo el resto — usuarios, roles, productos, precios, stock, pedidos,
   clientes, dashboard financiero — el único control es "hay un token válido". Un repartidor puede
   borrar el catálogo, reescribir precios de costo y leer las finanzas completas de la empresa.

2. **Hay tres caminos independientes a admin.** `PATCH /settings/profile` acepta `role_id` por mass
   assignment; `POST /users` no tiene ninguna autorización; y `change-password` reescribe el password
   del primer usuario de la tabla — casi siempre el admin — sin importar el ID de la URL.

3. **El upload de imágenes de producto no valida nada.** `ProductFormRequest` no tiene regla para
   `file` y la extensión sale de `getClientOriginalExtension()`. Un `.php` queda accesible bajo
   `/storage/img/products/`; con los nginx del repo eso es ejecución remota de código.

4. **El balance de cuenta corriente se puede sobreescribir por HTTP.** `current_balance` está en
   `$fillable` y `CustomersController::update` hace `fill($request->all())` sin FormRequest ni
   policy: un `PUT` borra la deuda de cualquier cliente sin dejar asiento ni rastro.

5. **El ledger de repartos tiene dos caminos abiertos al mismo estado corrupto que ya se parchó a
   mano en producción.** Los cargos se crean únicamente en la transición a `finished`; un pedido
   marcado como entregado después genera el cobro sin la deuda. Y borrar un reparto `finished` deja
   cargos `pending` huérfanos que además bloquean el cargo real por el dedupe. La migración
   `backfill_missing_charges_delivery_129` es la evidencia de que esto ya pasó.

6. **Un `PUT /orders/{id}` parcial destruye plata en silencio.** `prepareForValidation` inyecta
   `discount = 0` y `delivery_cost = 0` cuando el cliente no los manda, y `validated()` reescribe
   `total`. Editar solo las notas de un pedido le borra el descuento y lo desalinea del asiento ya
   contabilizado.

7. **Nadie es dueño de `products.stock`.** No existe una sola escritura a esa columna en todo `app/`,
   pero `OrderDetailQuantityValidator` valida cada línea contra ella. El valor lo mantiene, casi con
   certeza, un trigger de base de datos fuera del control de versiones — invisible, no testeable y
   sin ningún lock que evite sobreventa.

8. **La base de datos no se puede reconstruir desde las migraciones.** No hay `create` para ninguna
   tabla del core (`users`, `orders`, `products`, `customers`, `stocks`…). Sin schema reproducible no
   hay entorno local ni CI, y sin suite de tests no hay forma de validar ninguna de las correcciones
   de abajo.

9. **La performance está dominada por N+1 en los Resources.** El listado de productos, el endpoint
   más golpeado, hace ~81 queries por página; el detalle de un reparto de 60 pedidos suma ~120
   queries extra resolviendo contexto de asientos; cerrar un reparto dispara entre 500 y 800
   statements.

10. **Hay 28 rutas rotas y ~1.200 líneas de código de otro producto.** Cuatro rutas apuntan a
    métodos que no existen (500 garantizado, incluida `finance/dashboard/row-detail`), 24 son
    `create`/`edit` fantasma de `Route::resource`, y modelos/controllers de "meetups" e
    "inscriptions" siguen en el árbol junto a 17 MB de bundles React que ningún template sirve.

# P0 — Critical (8)

Todos verificados por lectura directa del archivo.

### SEC-01 · Escalada a admin vía update de perfil

- **Evidencia** — `Settings/ProfileController.php:32-36` valida 5 campos de perfil pero hace
  `$user->fill($request->all())`; `User::$fillable` incluye `role_id`, `email` y `password`.
- **Impacto** — Cualquier usuario autenticado se promueve a admin con
  `{"firstname":"a","lastname":"b","role_id":1}`. También permite cambiar su propio email y password
  sin el password actual.
- **Recomendación** — `fill($request->validated())` y sacar `role_id` de `$fillable`. El rol solo
  debe cambiarse por un endpoint admin.
- **Confianza** — Alta

### SEC-02 · change-password reescribe el password del primer usuario

- **Evidencia** — `Auth/ChangePasswordController.php:30`: `User::findOrfail($id)->first()`. El
  `->first()` se reenvía a `newQuery()`, así que devuelve el primer usuario de la tabla, no el de la
  URL. Sin policy y sin verificar el password actual.
- **Impacto** — Toma de control de la cuenta admin desde cualquier token:
  `PATCH /users/999/change-password` cambia el password del usuario de menor ID. La respuesta
  devuelve además el objeto del usuario.
- **Recomendación** — Bindear `User $user`, exigir y verificar `old_password`, gatear con policy
  (self o admin) y borrar el `->first()`.
- **Confianza** — Alta

### SEC-03 · CRUD de usuarios y roles sin autorización

- **Evidencia** — `UsersController` / `RolesController` están solo detrás de `auth:api`.
  `UserStoreRequest::authorize()` y `UserUpdateRequest::authorize()` devuelven `true`. No hay
  `UserPolicy` ni `RolePolicy` registradas.
- **Impacto** — `POST /users` con `role_id:1` crea una backdoor admin persistente; `PUT` toma
  cualquier cuenta; `DELETE` borra a los admins. Editar roles reescribe el modelo de permisos
  completo.
- **Recomendación** — Policies admin-only invocadas desde los FormRequests, o middleware de rol
  sobre el grupo de rutas de `users` y `roles`.
- **Confianza** — Alta

### SEC-04 · Upload de imágenes sin validar → probable RCE

- **Evidencia** — `ProductFormRequest::rules()` no tiene ninguna regla para `file`.
  `ImageTraitController::uploadOne():17` arma el nombre con `getClientOriginalExtension()` y escribe
  en el disco `public`, expuesto vía el symlink `public/storage`. Los nginx del repo ejecutan
  cualquier `\.php$` bajo el document root.
- **Impacto** — Subir `x.php` por `POST /products` (cualquier rol) y pedirlo en
  `/storage/img/products/…php` ejecuta código como el usuario de PHP-FPM. Sin eso, es XSS almacenado
  en el propio origen y relleno de disco sin límite.
- **Recomendación** — `'file' => 'nullable|image|mimes:jpg,jpeg,png,webp|max:4096'`; derivar la
  extensión del MIME validado, nunca del cliente; deshabilitar PHP en el directorio de uploads.
- **Confianza** — Alta (upload) / Media (que sea RCE, ver NV-04)

### DAT-01 · current_balance sobreescribible por HTTP

- **Evidencia** — `Customer::$fillable` incluye `current_balance`;
  `CustomersController::update:166-175` hace `fill($request->all())` sin FormRequest, sin validación
  y sin policy. Lo mismo en `store:38-53`.
- **Impacto** — Cualquier usuario — incluido el repartidor cuya rendición se reconcilia contra ese
  número — pone la deuda de cualquier cliente en cero sin asiento ni auditoría. Además el frontend
  puede pisarlo por accidente devolviendo un valor viejo del `CustomerResource`.
- **Recomendación** — Sacar `current_balance` de `$fillable` (solo `UpdateCustomerBalanceService`
  debe tocarlo), agregar `CustomerStore/UpdateRequest` y `CustomerPolicy`.
- **Confianza** — Alta

### DAT-02 · Cargos solo en la transición a finished

- **Evidencia** — `DeliveryObserver::updated:41-48` llama a `createChargesForFinishedDelivery`
  únicamente en `FINISHED`; la rama `CLOSED` solo crea pagos.
  `createChargesForFinishedDelivery:34-36` saltea todo pivot que no esté `delivered` en ese instante,
  y `DeliveryPolicy::updateOrder` permite editar pedidos "siempre".
- **Impacto** — Pedido marcado como entregado después del `finish`: al cerrar se crea el pago y se
  valida, aplicando un crédito sin el débito correspondiente. El saldo del cliente queda subvaluado
  por el total del pedido. Es el mismo síntoma que parchó
  `backfill_missing_charges_delivery_129`.
- **Recomendación** — Re-invocar `createChargesForFinishedDelivery` al inicio de la rama `CLOSED`
  (ya es idempotente por pedido) y al pasar un pivot a `delivered`; rechazar `updateOrder` si el
  reparto está `closed`.
- **Confianza** — Alta

### DAT-03 · Borrar un reparto finished deja cargos huérfanos que bloquean el real

- **Evidencia** — `DeliveryObserver::deleting:62-77` solo bloquea `CLOSED`. Los pivots caen por
  `ON DELETE cascade`, pero los `account_entries` `pending` quedan: no hay FK de `source_id` a
  `orders` ni limpieza. El dedupe de `DeliveryLedgerService:44` los ve y saltea el cargo nuevo.
- **Impacto** — Los pedidos vuelven a `ready_to_ship`, se entregan en otro reparto y ya no generan
  deuda; al cerrar se aplican solo los créditos. Los cargos huérfanos no se pueden validar nunca
  porque `AccountEntryPolicy::validate` rechaza lo que no está `not_validated`.
- **Recomendación** — En `deleting`, borrar o reasignar los asientos `pending` de los pedidos del
  reparto; o prohibir borrar repartos pasados de `in_progress`.
- **Confianza** — Alta

### SEC-05 · Exports de PII y de costos sin autenticación

- **Evidencia** — `routes/web.php:24-27` registra tres rutas en el grupo `web` sin ningún middleware
  de auth: `listado/exportar` → `SummaryController@export` y `products/export` →
  `ProductsController@export`.
- **Impacto** — Cualquiera en internet baja el PDF de hoja de ruta (nombres, direcciones y ventanas
  de visita de clientes por zona y fecha, iterables por fuerza bruta) y el `products.xlsx` completo
  con `price_purchase` y márgenes.
- **Recomendación** — Mover ambas al grupo `auth:api` de `routes/api.php`, o envolverlas en
  `auth`/`signed`. La tercera (`comprobante/{id}`) apunta a un método inexistente: borrarla.
- **Confianza** — Alta

# P1 — High (22)

### SEC-06 · Todo el resto de recursos sin autorización

- **Evidencia** — Grep de `authorize(` / `Gate::` / `->can(` / `role_id` en `app/Http/Controllers`
  solo da hits en `DeliveriesController`, `AccountEntriesController` y un filtro de lectura en
  `OrdersController:176`. Todos los demás FormRequests hacen `authorize(){ return true; }`.
- **Impacto** — Un token de repartidor borra el catálogo, reescribe `price_unit` y `price_purchase`,
  crea y destruye movimientos de stock, borra pedidos y reasigna zonas.
- **Recomendación** — Policy por modelo registradas en `AuthServiceProvider`, o como mínimo un
  middleware de rol sobre los verbos de escritura.
- **Confianza** — Alta

### SEC-07 · Dashboard financiero sin ninguna autorización

- **Evidencia** — Las tres rutas `finance/dashboard*` están solo detrás de `auth:api`;
  `FinanceDashboardController` no tiene `authorize()`, policy ni chequeo de rol.
- **Impacto** — Cualquier usuario autenticado lee ventas, gastos, cobranzas, márgenes y desgloses
  por cliente y por zona de la empresa completa.
- **Recomendación** — `FinancePolicy` o gate chequeado en el controller.
- **Confianza** — Alta

### SEC-08 · Tokens de reset de password eternos y reutilizables

- **Evidencia** — `Auth/ResetPasswordController::reset:28-48` busca por token sin chequear
  `created_at`, no borra la fila al usarla y no invalida los JWT existentes.
  `ForgotPasswordController::storeResetToken` guarda el `Str::random(64)` en texto plano.
- **Impacto** — Cada link de reset emitido es una credencial permanente y replicable: un mail viejo,
  una casilla filtrada o un log de proxy de hace un año siguen sirviendo hoy. Un leak de solo lectura
  de `password_resets` es toma de control directa.
- **Recomendación** — Usar `Password::broker()`, o agregar expiración
  (`created_at >= now()-60min`), borrar la fila después de usarla y guardar el hash del token.
- **Confianza** — Alta

### SEC-09 · forgot-password valida el campo equivocado y explota con usuario inexistente

- **Evidencia** — `ForgotPasswordController::sendResetLinkEmail:24-31` exige
  `password|required|min:6|confirmed` en un endpoint de "olvidé mi contraseña", nunca valida `email`,
  y pasa un `null` a `storeResetToken(User $user, …)`. El link se arma con
  `strstr($request->input('routeSuffix'), ':', true)`, input del cliente.
- **Impacto** — El endpoint es inusable como está y el 500-vs-200 es un oráculo de enumeración de
  usuarios. El destino del link enviado por mail es parcialmente controlado por el atacante.
- **Recomendación** — Validar `email => required|email`, responder siempre 200, quitar la regla
  `password` y armar el link desde config del servidor.
- **Confianza** — Alta

### SEC-10 · Login sin protección de fuerza bruta + oráculo de enumeración

- **Evidencia** — `Http/Kernel.php:41-45`: un único `throttle:260,1` global cubre todo, incluido
  `auth/signin` y `password/reset/{token}`. `SessionsController::identify:24-36` es público y
  **devuelve el email** de la cuenta. `UserStoreRequest` permite passwords de 6 caracteres.
- **Impacto** — ~374.000 intentos por día por IP contra una política de 6 caracteres, con los
  usuarios válidos obtenidos gratis del `identify`. También permite adivinar tokens de reset sin
  límite.
- **Recomendación** — `throttle:5,1` por usuario+IP en `signin` y en las rutas de password; que
  `identify` devuelva un booleano; subir el mínimo a `min:8|pwned:100` como ya usa
  `AccountController`.
- **Confianza** — Alta

### DAT-04 · PUT /orders/{id} parcial borra descuento y costo de envío

- **Evidencia** — `OrderUpdateRequest::prepareForValidation:75-84` mergea `delivery_cost => 0` y
  `discount => 0` cuando el input viene vacío; ambas reglas son `nullable`, así que siempre llegan a
  `validated()`, que además reescribe `total_bruto` y `total`. `authorize()` devuelve `true`.
- **Impacto** — Un pedido con `discount=10` y `delivery_cost=2000` queda en 0 y 0 al mandar solo
  `{"notes":"llamar antes"}`. Si ya tenía asiento contable, pedido y ledger divergen sin rastro.
- **Recomendación** — Mergear defaults solo con guardas `$this->has(...)`; recalcular totales desde
  los valores persistidos; bloquear cambios de dinero en pedidos ya entregados o contabilizados.
- **Confianza** — Alta

### DAT-05 · Cobros fuera de ruta contra un reparto cerrado quedan pending para siempre

- **Evidencia** — `AccountEntriesController:111-134` fuerza `PENDING` cuando viene `delivery_id`;
  `StoreAccountEntryRequest:26` solo valida `exists:deliveries,id`, sin restringir el estado. Los
  `pending` solo se validan en la transición `finished→closed`, que ya ocurrió.
- **Impacto** — La caja que el repartidor entregó después del cierre aparece en
  `collectedByPaymentMethodOffRoute()` como cobrada, pero nunca baja la deuda del cliente. La fila no
  se puede validar desde la UI.
- **Recomendación** — Rechazar `delivery_id` de repartos `closed`, o guardar el asiento como
  `not_validated` en ese caso.
- **Confianza** — Alta

### DAT-06 · Editar un pedido del reparto después del cierre deja el asiento viejo

- **Evidencia** — `DeliveryService::updateDeliveryOrder:328-401` reescribe `collected_amount` y
  recrea `delivery_order_payments`; `DeliveryPolicy::updateOrder:117-125` lo permite sobre repartos
  `closed`. El `AccountEntry` creado al cerrar nunca se actualiza.
- **Impacto** — Corregir un tipeo de 30.000 a 3.000 deja el pivot en 3.000 y el ledger más
  `current_balance` en 30.000.
- **Recomendación** — Bloquear `updateOrder` con el reparto `closed`; si la corrección debe
  permitirse, emitir un asiento compensatorio.
- **Confianza** — Alta

### DAT-07 · Borrar un pedido no revierte su cargo contable

- **Evidencia** — `OrdersController::destroy:108-117` hace `Order_details::destroy($ids)` y
  `$order->delete()` sin transacción, sin `authorize()` y en hard delete (`Order` no usa
  `SoftDeletes`). El `charge` con `source_id=<id borrado>` sobrevive sin FK.
- **Impacto** — El débito validado queda en `current_balance` para siempre, sin nada a lo que
  apuntar. Una falla entre los dos deletes deja `order_details` huérfanos.
- **Recomendación** — Envolver en `DB::transaction`, rechazar el borrado si el pedido tiene asientos
  o pivots no fallidos, o emitir una nota de crédito.
- **Confianza** — Alta

### DAT-08 · type y direction son independientes: un "Pago" puede aumentar la deuda

- **Evidencia** — `StoreAccountEntryRequest:19-31` valida `type` y `direction` por separado contra
  sus enums completos. `UpdateCustomerBalanceService::deltaForEntry` depende **solo** de
  `direction`, mientras la UI etiqueta por `type`. `AccountEntryType::manualAllowed()` tiene cero
  call sites.
- **Impacto** — `{type: payment, direction: debit, amount: 50000}` aumenta la deuda 50.000 mientras
  el listado muestra "Pago $50.000". Un `type=charge` manual duplica un débito que el cierre va a
  crear de nuevo (el dedupe no lo ve: usa `source_type='manual'`).
- **Recomendación** — Mapa `type → direction` obligatorio en el FormRequest y restringir la creación
  manual a `manualAllowed()`.
- **Confianza** — Alta

### DAT-09 · El precio unitario de cada línea lo pone el cliente

- **Evidencia** — `OrderDetailsStoreRequest:26` / `UpdateRequest:25`:
  `'price_unit' => 'required|numeric|min:0.01'`, nunca comparado contra `products.price_unit`,
  `price_min` ni `percentage_may`.
- **Impacto** — `{price_unit: 1, quantity: 100}` pasa todas las validaciones. Toda la maquinaria de
  `discount_matches_promotion` queda sin sentido si el precio base es libre.
- **Recomendación** — Derivar `price_unit` en el servidor desde el producto y la lista de precios
  del cliente.
- **Confianza** — Alta (comportamiento) / Media (si es intencional)

### ARQ-01 · Las migraciones no pueden reconstruir la base

- **Evidencia** — `Schema::create` cubre solo `promotions`, `promotion_products`, `deliveries`,
  `delivery_orders`, `delivery_order_payments`, `account_entries` y

  Tampoco hay `jobs`, `failed_jobs` ni `password_resets`.
- **Impacto** — `migrate:fresh` falla de entrada: no hay entorno local ni CI reproducible. Sin eso
  no se puede validar ninguna corrección salvo contra producción.
- **Recomendación** — Migración baseline squasheada desde el schema de producción (`schema:dump`),
  incluyendo triggers, más `queue:table` y `queue:failed-table`.
- **Confianza** — Alta

### ARQ-03 · StockController: tres acciones tipadas contra clases inexistentes

### ARQ-04 · NotificationsController roto en cuatro de sus rutas

- **Evidencia** — El resource registra `store`, `show`, `update` y `destroy`; el controller solo

- **Impacto** — Tres rutas dan 500 y el `DELETE` da fatal. `index` consulta una tabla

### PRF-01 · ProductResource: 2 queries por producto en el listado más golpeado

- **Evidencia** — `ProductsController::paginatedQuery:200` hace `->with('activePromotions')` y nada
  más; `ProductResource:32` lee `$this->category->name` (belongsTo nunca eager-loaded) y `:42` llama
  `getImages()`, que ejecuta un `products JOIN images` fresco por modelo.
- **Impacto** — `1 + 2N` queries por página, N = 40 por default → ~81 queries por request de
  `GET /products`, el endpoint del selector de productos en la carga de pedidos.
- **Recomendación** — `->with(['category:id,name','image'])` — definiendo un
  `hasOne(Image::class,'id_product')` — y leer con `optional()`.
- **Confianza** — Alta

### PRF-02 · AccountEntryResource: 2 queries por asiento, sin arreglo posible desde el controller

- **Evidencia** — `AccountEntryResource:12` → `AccountEntrySourceHelper::resolveDeliveryContext`,
  que hace `Delivery::find()` o `DeliveryOrder::with('delivery')->find()` por fila. Es polimorfismo
  hecho a mano sobre `source_type`/`source_id`: ningún `with()` upstream lo previene.
- **Impacto** — `2N` queries extra en cuatro call sites. `DeliveriesController::show` y
  `::accountEntries` usan `->get()` sin paginar: un reparto de 60 pedidos suma ~120 queries, cada
  una escaneando `account_entries` completa.
- **Recomendación** — Batch-resolve en el controller (dos `whereIn`) y pasar el mapa por
  `->additional([...])`; paginar `accountEntries`.
- **Confianza** — Alta

### PRF-03 · Cerrar un reparto dispara 500-800 statements

- **Evidencia** — `DeliveryLedgerService:44` hace un `exists()` por pedido dentro del loop; `:50` y
  `:93` hacen `Customer::find()` por fila ignorando el `load(['deliveryOrders.order.customer'])` de
  `:74`; `:159` hace `$entry->update()` uno por uno, y cada uno dispara el observer → un
  `UPDATE customers`.
- **Impacto** — ~8-10 queries por pedido. Para 40-80 pedidos, un solo
  `POST /deliveries/{id}/close` ejecuta 500-800 statements dentro de una transacción.
- **Recomendación** — Subir el `exists` a un `whereIn` antes del loop (el patrón correcto ya existe
  en `:78`); usar el customer eager-loaded; agregar el delta por cliente en un solo `UPDATE`.
- **Confianza** — Alta

### PRF-04 · Faltan dos índices en account_entries que 9 queries calientes necesitan

- **Evidencia** — `create_account_entries_table:34` define un solo índice:
  `['customer_id','occurred_at']`. Falta `(type, direction, occurred_at)` para
  `FinanceDashboardService::baseCollectionsQuery:396-402` y sus dos gemelas (`customer_id` es
  opcional, así que la columna líder queda sin bindear); y falta `(source_type, source_id)` para
  `DeliveriesController:91` y `:123`, `DeliveryLedgerService:44`/`:78`/`:141`, los `whereExists` de
  `FinanceDashboardService:422` y `:528`, y `Delivery.php:185`.
- **Impacto** — `GET /finance/dashboard` corre `baseCollectionsQuery` cinco veces → cinco full scans
  más los joins. El peor caso del segundo índice es `DeliveryLedgerService:44`: N full scans en un
  loop.

  cantidad nueva sin devolver la existente de la línea: subir de 8 a 10 con 3 disponibles se rechaza
  aunque solo falten 2.

### NV-02 · ¿Existe la columna `users.username`?

- **Qué se sabe** — `AccountController::updateCredentials` la valida y asigna,
  `SessionsController::identifier()` ramifica sobre ella, pero no está en `$fillable` y el único hit
  en `database/` es `UsersTableSeeder.php:18`.
- **Cómo verificar** — `SHOW COLUMNS FROM users;`
- **Si se confirma** — Si no existe, `updateCredentials` y la rama `username` de `signin`/`identify`
  fallan a nivel SQL.

### NV-03 · ¿Existen `jobs`, `failed_jobs` y `password_resets` en producción?

- **Qué se sabe** — Ninguna tiene migración en el repo, pero `storeResetToken` escribe
  `password_resets` directamente, así que esa al menos debe existir.
- **Cómo verificar** — `SHOW TABLES LIKE '%jobs%';`
- **Si se confirma** — Generar las migraciones faltantes desde el schema real antes de tocar el
  driver de colas (QUE-01).

### NV-04 · ¿El nginx de producción ejecuta PHP bajo el document root?

- **Qué se sabe** — Los tres nginx del repo tienen
  `location ~ \.php$ { fastcgi_pass app:9000; }`. El `Procfile` sugiere
  `heroku-php-nginx -C nginx_app.conf`, el Dockerfile sugiere otra cosa.
- **Cómo verificar** — Inspeccionar el nginx efectivo del entorno de deploy.
- **Si se confirma** — Determina si SEC-04 es RCE o "solo" XSS almacenado. En cualquier caso el fix
  de validación es el mismo y no debe esperar esta verificación.

### NV-05 · ¿El `JWT_SECRET` de producción es el commiteado?

- **Qué se sabe** — `.env.testing` está trackeado con un secreto de 32 caracteres con pinta de real;
  `.env.example` trae `noclue`.
- **Cómo verificar** — Comparar contra el `.env` del servidor.
- **Si se confirma** — Forjado de tokens admin. Rotar `JWT_SECRET` y `APP_KEY` igual, por precaución.

### NV-06 · Modo de falla de la regla `pwned:100`

- **Qué se sabe** — `valorin/pwned-validator` (lock: 1.3.9) se usa en `ResetPasswordController:25` y
  `AccountController:60`. Es una llamada HTTP saliente a `api.pwnedpasswords.com` dentro del
  request — la única integración externa real de la app, además de SMTP. `vendor/` está vacío
  localmente (volumen Docker `miyi_vendor`).
- **Cómo verificar** —
  `docker compose -f docker-compose.local.yml exec app cat vendor/valorin/pwned-validator/src/PwnedValidator.php`
- **Si se confirma** — Si falla cerrado, una caída de HIBP bloquea todos los cambios de password. Si
  falla abierto y sin timeout corto, agrega latencia al request. En ambos casos conviene un timeout
  explícito.

# Notas de metodología

## Contradicciones entre agentes, resueltas

**`groupBy` + `paginate()`.** Un análisis reportó que el `total` de la paginación de productos era el
conteo de un solo grupo. Es incorrecto para Laravel 8: `Query\Builder::runPaginationCountQuery`
envuelve la query en `select count(*) from (…) as aggregate_table` cuando hay `$groups` o
`$havings`, así que el total es correcto. Se reportó solo el costo real (la temp table extra) en
PRF-08.

**`PUT /stock/{id}`.** Un análisis lo describió como no-op silencioso con 200; otro como fatal. Es
fatal: el binding implícito no matchea (parámetro `{stock}` vs variable `$order`), así que el
resolver de dependencias intenta `container->make('App\Http\Controllers\Api\V1\Order')` y lanza
`BindingResolutionException` → 500. La advertencia de que "arreglar" el import haría que borrar stock
borre pedidos sigue en pie (ARQ-03).

## Falsos positivos descartados

Verificado y **no** reportado: la inyección SQL (las ~70 apariciones de
`DB::raw`/`whereRaw`/`selectRaw` usan SQL estático o bindings `?`; los dos casos que interpolan
castean a `(float)` o usan `havingRaw('… >= ?')`); `ChangePasswordController` guardando password en
texto plano (el mutator `User::setPasswordAttribute` lo hashea); `AccountEntriesController` sin
autorización (sí la tiene, correctamente, en los FormRequests y con `$this->authorize()`);
`ProductsExport` como código muerto (está en uso vía `Excel::download`). Tampoco hay TODO/FIXME
reales — los dos hits del grep son la palabra española "Todos" — ni `dd()`/`dump()` olvidados.

## Cómo se produjo

Seis análisis paralelos (seguridad; base de datos y performance; arquitectura; lógica de negocio e
integridad; colas e integraciones; testing y código muerto), consolidados: deduplicados, con los P0
y P1 verificados por lectura directa del archivo y las contradicciones resueltas. Las severidades
reflejan explotabilidad y dinero en riesgo, no cantidad de código afectado.
